## What the semantic gate actually establishes

The **active** `release_semantic_gate.py` first checks release bytes, then imports the strategy module and runs deterministic tests on synthetic OHLC. It checks candidate/version metadata, expected parameter names, absence of certain C-owned terms in parameter schema, discoverable OHLC convention, repeated-signal equality, no mutation of the provided history, permitted signal representation, and one grossly invalid value per named parameter. It does **not** use an LLM reviewer, and does **not** validate the full frozen B hypothesis or all entry/exit cases. The historical `semantic_gate_v2.py` tests different conditions and interface; do not merge its evidence into the active gate without a traceable execution.

## Principal risks and future engineering options — not implemented

1. Run generated code in a separate least-privilege process/container with read-only Operator runner/policy mounts, no outbound network, limited data directories, resource caps and a disposable filesystem.
2. Perform an AST-based import/call/file-access review **before any dynamic import**; deny unknown modules and re-validate runtime dependencies. Static analysis alone cannot prove absence of dynamic imports or external access.
3. Add immutable ownership checks on Stage 1 runner and governance rules, with Operator approval for any change.
4. Consider **independent LLM-assisted semantic review** against the frozen B specification, with a separate model/context, traceable discrepancy report and Human adjudication. This is proposed, not observed or authorized.

**Verdict:** Structural, identity and narrow behavioral controls exist and have unit evidence. An enforceable code-execution sandbox, active C import allowlist and independent semantic review are **not demonstrated**. Never claim generated Python is confined merely because a prompt says “No network/files.”
